# CSS Architecture - モジュール設計（Rev.4 正式版）

## 概要

本書は「hiro-san 山歩きサイト V5」の CSS 設計方針を定義した設計基準書である。

本プロジェクトでは、単に画面を表示するための CSS ではなく、

- 保守性
- 可読性
- 拡張性
- 変更容易性
- 役割分離

を重視したモジュール構成を採用している。

CSS はサイト全体の共通資産として管理し、ページ追加や機能追加が発生しても既存ファイルへの影響を最小限に抑えることを目的とする。

本書は CSS 台帳・レビュー台帳・To-Be 台帳・変更管理台帳の設計基準として利用する。

---

# Rev.4 設計理念

Rev.4では「動作するCSS」ではなく、

**あとから誰が見ても理解でき、安心して修正できるCSS**

を目標とする。

そのため以下の5つを基本理念とする。

## 1. 責務を明確にする

1つのCSSファイルには1つの責務だけを持たせる。

例

- variables → 変数
- header → ヘッダー
- card → カード
- home → HOME専用

役割が混在することを避ける。

---

## 2. 共通化は必要最小限

共通化できるから共通化するのではなく、

「複数ページで同一仕様が維持されるもの」

だけを共通化する。

無理な共通化は行わない。

---

## 3. ページ単位の独立性

Pages層は他ページへ影響しない。

HOMEを修正しても

Aboutには影響しない。

これを基本原則とする。

---

## 4. Componentsは再利用を前提とする

Componentは

- ボタン
- カード
- フォーム

など、

ページを超えて利用されるUI部品のみ配置する。

ページ専用デザインはComponentsへ入れない。

---

## 5. 保守性を最優先とする

CSSは書くことより

「あとから修正すること」

の方が圧倒的に多い。

そのため

・どこを修正するべきか

・影響範囲はどこか

がすぐ分かる構造を維持する。

---

# 設計方針

本プロジェクトでは以下の優先順位で設計を行う。

① 保守性

② 可読性

③ 責務分離

④ 拡張性

⑤ コード量削減

コードを短くすることよりも、

構造が理解しやすいことを優先する。

---

# Rev.4で確立した設計原則

レビューを通じて以下を正式ルールとする。

・Baseは全体基盤のみを管理する。

・Layoutは共通レイアウトのみ管理する。

・Componentsは再利用部品のみ管理する。

・Pagesはページ専用デザインのみ管理する。

・Responsiveは共通レスポンシブのみ集中管理する。

・ページ固有レスポンシブは各ページ内で管理する。

・Components固有レスポンシブは各Componentsで管理する。

これをRev.4の正式設計とする。

# レイヤー構成

Rev.4では、CSSを責務ごとに4つのレイヤーへ分割して管理する。

```
Base
　↓
Layout
　↓
Components
　↓
Pages
```

上位レイヤーほど変更頻度は低く、
下位レイヤーほどページ固有の実装を担当する。

各レイヤーは明確な責務を持ち、
役割が重複しないことを設計原則とする。

---

サイト全体で使用する基本定義を管理する。

デザインシステムの基盤となるレイヤーであり、
他レイヤーから参照される。

Base自身は他レイヤーへ依存しない。

---

|ファイル|責務|変更頻度|
|---------|------|---------|
|variables.css|CSS変数・デザインシステム|低|
|reset.css|ブラウザリセット・body基本設定|低|
|typography.css|見出し・段落など文字設定|低|

・色

・余白基準

・Radius

・Shadow

・Transition

・body

・html

・img

・table

・button

などサイト全体へ影響する要素

---

## 管理しないもの

ページ固有デザイン

カード

ボタン

フォーム

ヘッダー

フッター

---

# レイヤー間の依存関係

```
Base
　↑
Layout
　↑
Components
　↑
Pages
```

PagesはComponentsを利用できる。

ComponentsはLayoutを利用できる。

LayoutはBaseを利用できる。

逆方向の依存は禁止する。

# Rev.4 レビューで確定した責務

レビュー結果より、以下を正式ルールとする。

■ Base
デザインシステムのみ管理する。

■ Layout
サイト共通構造のみ管理する。

■ Components
複数ページで利用されるUIのみ管理する。

■ Pages
ページ専用デザインのみ管理する。

■ Responsive
共通レスポンシブのみ集中管理し、
ページ専用レスポンシブは各ページで管理する。

これをRev.4正式アーキテクチャとする。

# style.css の役割

style.css は各CSSを読み込むマスターファイルである。

このファイルにはデザインを記述しない。

役割は

・読み込み順の管理

のみとする。

---

# @import の順序

読み込み順は以下を厳守する。

```css
/* ======================================
   BASE
====================================== */

@import "base/variables.css";
@import "base/reset.css";
@import "base/typography.css";

/* ======================================
   LAYOUT
====================================== */

@import "layout/common.css";
@import "layout/header.css";
@import "layout/navigation.css";
@import "layout/footer.css";
@import "layout/responsive.css";

/* ======================================
   COMPONENTS
====================================== */

@import "components/button.css";
@import "components/card.css";
@import "components/form.css";
@import "components/pagination.css";

/* ======================================
   PAGES
====================================== */

@import "pages/home.css";
@import "pages/records-index.css";
@import "pages/record.css";
@import "pages/logs-index.css";
@import "pages/about.css";
@import "pages/blog.css";
@import "pages/others.css";
@import "pages/error.css";
```

---

# 読み込み順の理由

## Base

CSS変数や基本設定を定義する。

他の全ファイルが参照するため最初に読み込む。

---

## Layout

サイト全体レイアウトを定義する。

ComponentsやPagesはLayoutの上に構築される。

---

## Components

共通部品を定義する。

PagesはComponentsを利用する。

---

## Pages

最も具体的なスタイルを定義する。

必要に応じてComponentsを上書きできる。

---

# 読み込み順変更の禁止

以下は禁止する。

Pagesより前にComponentsを書き換えること。

Layoutより前にPagesを読み込むこと。

Baseより前に他ファイルを読み込むこと。

読み込み順は設計ルールであり変更しない。

# CSS設計ルール

Rev.4では、CSSを追加・修正する際の判断基準を明確化する。

・レビュー品質の向上

・保守性の向上

・修正箇所の明確化

を実現する。

---

# 基本原則

CSSは

「どこに書けるか」

ではなく

「どこへ書くべきか」

で判断する。

コード量より責務を優先する。

---

# Rule1　責務を最優先する

CSSファイルは

一つの責務だけを持つ。

例

header.css

↓

ヘッダー以外を書かない。

button.css

↓

ボタン以外を書かない。

home.css

↓

HOME専用のみを書く。

---

# Rule2　共通化の判断基準

以下を満たした場合のみ共通化する。

□ 複数ページで使用される

□ 今後も同じ仕様になる

□ 名前だけではなく内容も同じ

この3条件を満たした場合のみ
ComponentsまたはLayoutへ移動する。

---

# Rule3　名前だけで共通化しない

同じセレクタ名でも

内容が違う場合は共通化しない。

例

.records-list

ページA

display:flex;

ページB

display:grid;

これは共通化しない。

レビューでは

名前ではなく

内容を比較する。

---

# Rule4　Components化する条件

以下を満たした場合

Componentsへ移動する。

・2ページ以上で利用

・デザインが共通

・今後も増える可能性がある

例

Button

Card

Form

Pagination

---

# Rule5　Layoutへ置く条件

Footer

---

# Rule6　Pagesへ置く条件

Aboutだけ

Blogだけ

検索画面だけ

# Rule7　Baseへ置く条件

サイト全体の設計基盤だけを管理する。

例

# Rule8　セレクタ重複時の判断

# Responsive設計

## 基本方針

Rev.4では、

「レスポンシブを一か所へ集める」

ことを目的とはしない。

目的は

**保守しやすく責務が分かる構造**

を維持することである。

そのため、

レスポンシブも責務に従って配置する。

---

# 基本ルール

Responsiveは

共通

Components

Pages

の3種類に分類する。

```
Responsive
├── 共通
├── Components
└── Pages
```

---

# ① 共通Responsive

配置

```

```

ここには

サイト全体で共通になるレスポンシブのみ配置する。

例

h1

h2

h3

container

section

footer

共通余白

など。

---

# ② Components Responsive

Component固有のレスポンシブは

各Component内で管理する。

例

```
card.css
```

```css

}

@media(max-width:768px){

.record-card{

}

}
```

カードだけを見ると

Desktop

Mobile

両方確認できる。

これを基本とする。

---

# ③ Pages Responsive

ページ専用レスポンシブは

各Page内で管理する。

例

```

record.css

logs-index.css
```

など。

HOMEだけ変更したい場合

home.cssだけ見ればよい。

---

# なぜ分散管理するのか

以前は

Responsiveを

全部

responsive.css

へ集約する案も検討した。

しかし

レビューの結果

以下の問題が判明した。

・DesktopとMobileが離れる

・修正箇所を探しにくい

・Page責務が曖昧になる

・Component単位で把握できない

そのため

現在の方式を正式採用する。

# 保守・変更管理ルール

## 目的

本章は、CSSを長期運用するための保守・変更管理ルールを定義する。

修正時に担当者や時期が変わっても、
同じ判断基準で運用できることを目的とする。

---

# 基本方針

CSSの保守では

「まず修正する」

のではなく

「変更が必要か」

を判断する。

必要最小限の変更を原則とする。

---

# 保守判断フロー

新しいデータや画面変更が発生した場合は、
以下の順で判断する。

```
変更要求
    │
    ▼
現状で対応可能か？
    │
 ┌──┴──┐
 │      │
YES    NO
 │      │
終了    ▼
     既存CSS修正で対応可能か？
           │
      ┌───┴───┐
      │       │
     YES      NO
      │       ▼
      │   Component追加で対応可能か？
      │          │
      │     ┌────┴────┐
      │     │         │
      │    YES        NO
      │     │         ▼
      │     │    新規CSS作成
      ▼
既存CSS修正
```

---

# 保守区分

保守作業は4種類に分類する。

|区分|内容|対応|
|----|----|----|
|①|現状で対応可能|変更なし|
|②|既存CSS修正|既存ファイル修正|
|③|Component追加|componentsへ追加|
|④|新規CSS追加|新規ファイル作成|

---

# 区分①　変更不要

以下の場合はCSSを変更しない。

・データ追加のみ

・レコード追加

・画像追加

・ブログ記事追加

・検索対象追加

CSSはそのままとする。

---

# 区分②　既存CSS修正

既存責務の範囲で対応できる場合。

例

文字サイズ変更

余白変更

色変更

ボタン幅変更

Header高さ変更

など。

新しい責務は増やさない。

---

# 区分③　Component追加

複数ページで再利用するUIが増える場合。

例

Badge

Modal

Tooltip

Alert

Dialog

など。

componentsへ追加する。

---

# 区分④　新規CSS追加

責務が新しく増える場合。

例

Galleryページ

Profileページ

Timelineページ

専用レイアウト

など。

新しいCSSファイルを作成する。

---

# 修正優先順位

修正は以下の順で検討する。

① Pages

↓

② Components

↓

③ Layout

↓

④ Base

影響範囲が小さいレイヤーから修正する。

---

# CSS追加禁止事項

以下は禁止する。

・別責務へ追記する。

・他ページ専用CSSを書く。

・名前だけで共通化する。

・固定値を乱用する。

・コメントを省略する。

---

# 変更履歴

変更を行った場合は
変更管理台帳へ記録する。

最低限記録する項目は以下とする。

|項目|内容|
|----|----|
|変更日|実施日|
|対象CSS|ファイル名|
|対象セレクタ|変更箇所|
|変更内容|概要|
|理由|変更理由|
|影響範囲|関連ページ|
|レビュー|確認状況|

---

# CSS台帳との連携

変更時は

CSS台帳

レビュー台帳

To-Be台帳

変更管理台帳

との整合を確認する。

設計書だけを更新する運用は禁止する。

---

# レビュー実施タイミング

レビューは以下の場合に実施する。

・新規ページ追加

・Component追加

・Layout変更

・デザイン変更

・大規模リファクタリング

軽微な色変更などは対象外とする。

---

# 定期レビュー

CSSは継続的に見直す。

目安は以下とする。

・大きな機能追加後

・半年ごと

・年間レビュー

レビューでは

責務

重複

共通化

コメント

保守性

を確認する。

---

# Rev.4運用方針

CSSは資産である。

短期的な修正を優先せず、

将来の保守性を維持することを最優先とする。

そのため、

「どこへ追加するか」

「本当に追加が必要か」

を常に確認してから実装を行う。

# 運用ルール・レビュー手順

## 目的

本章では、CSS設計を継続的に維持するための運用ルールを定義する。

設計書・CSS・管理台帳を常に一致させることを目的とする。

---

# 基本原則

CSSを変更する場合は、次の順序で作業を行う。

1. 変更内容を確認する
2. 保守区分（①～④）を判断する
3. 修正対象ファイルを決定する
4. CSSを修正する
5. ブラウザで確認する
6. 必要に応じて台帳を更新する
7. レビューを実施する

この手順を省略しない。

---

# 実装前チェック

実装前に必ず確認する。

|確認項目|内容|
|--------|----|
|責務|どのレイヤーの責務か|
|影響範囲|他ページへ影響するか|
|重複|既存セレクタで対応できないか|
|変数|CSS変数を利用しているか|
|Responsive|Mobile対応が必要か|

---

# 実装後チェック

CSS修正後は以下を確認する。

- レイアウト崩れがない
- PC表示確認
- スマートフォン表示確認
- Hover動作確認
- Focus確認（必要な場合）
- 余白確認
- 色確認
- コメント確認

---

# レビュー観点

レビューでは次の7項目を確認する。

|No|確認内容|
|---|---------|
|1|責務が適切か|
|2|共通化できるか|
|3|重複がないか|
|4|命名が適切か|
|5|コメントが適切か|
|6|Responsive配置が適切か|
|7|保守性が維持されているか|

---

# コメントルール

すべてのCSSファイルは統一コメントを使用する。

例

```css
/* ======================================
   COMPONENTS LAYER: CARD
   Card component styles
====================================== */
```

各セクションもコメントで区切る。

例

```css
/* ------------------------------
   Record Card
------------------------------ */
```

コメントは削除しない。

---

# セレクタ追加ルール

新しいセレクタを追加する場合は、

既存セレクタを確認してから追加する。

追加前に確認すること。

- 名前が重複しないか
- 同じ役割が存在しないか
- Components化できないか

---

# CSS変数ルール

色・サイズ・余白・Radius・Shadowなどは、

可能な限りCSS変数を利用する。

固定値は必要最小限とする。

例

```css
color: var(--color-primary);
```

|Component|各Component|

---

# 命名ルール

命名は役割を表す名前とする。

例

```
.record-card
.home-concept
.logs-filter
```

# 台帳更新ルール

以下の場合は台帳更新を行う。

|変更内容|更新対象|
|---------|---------|
|CSS追加|CSS台帳|
|レビュー実施|レビュー台帳|
|改善方針変更|To-Be台帳|

# レビュー完了条件

レビュー完了と判断できる条件。

- 責務が整理されている
- 重複が解消されている
- Responsive配置が適切
- コメントが統一されている
- 保守性が維持されている
